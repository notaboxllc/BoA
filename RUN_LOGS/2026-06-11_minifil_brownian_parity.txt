PART 1 — The real CPU-vs-GPU difference: a sqrt(10) Brownian bug
================================================================================
jba viewing frames: CPU myosin pieces "knocked all over"; GPU "much milder". Measured (body
equalized first via the 1/10 body scale below):
  rod-center mean step:  CPU 17.42 nm/frame   GPU 5.51 nm/frame   ratio 3.16 = sqrt(10)
Root cause: GPU move kernel scales Brownian by sqrt(2kT/deltaT) (GPUMoveThing.java:5227, deltaT=1e-4);
CPU calcRandomForces scales by 1/brownianDeltaT (Thing.java:1051, brownianDeltaT=1e-5) while
integration uses deltaT -> FDT-breaking mismatch; CPU diffuses ~10x too fast in variance.
brownianApplyInt = (int)(brownianDeltaT/deltaT) = (int)0.1 = 0, but `counter>=0` is always true,
so cadence is every-step regardless (same as the correct brownianApplyInt=1). Only the MAGNITUDE
was wrong. The DEFAULT brownianDeltaT_init = deltaT_init was already correct; 52 param files
override it to 1e-5.

jba: deltaT and brownianDeltaT were always meant to be identical; brownianDeltaT is residual.
Fix: REMOVE brownianDeltaT; Brownian always uses deltaT.
  Env.java: delete Parameter + _init; brownianApplyInt = 1.
  Thing.java:1050: bDt = Env.deltaT.getValue().
Unknown "brownianDeltaT:" lines in old configs are non-fatal (loader logs one "misunderstanding").

Blast radius: only configs with deltaT != brownianDeltaT change. Checked:
  glidingAssay500_val / _short : 1e-5 / 1e-5  -> MATCHED, no-op (gliding validation preserved)
  contractilityAssay_gpu       : 1e-5 / 1e-5  -> MATCHED, no-op
  boa10-singleMiniFil          : 1e-4 / 1e-5  -> corrected (CPU thermal drops sqrt(10))
  boa10-64Seg-dyn-short        : 1e-4 / 1e-5  -> corrected
  boa10-miniFil-staticActin    : 1e-4 / 1e-5  -> corrected
jba: Lp benchmark configs ran deltaT==brownianDeltaT==1e-5, so Lp is unaffected (no-op there).

Validation (boa10-singleMiniFil, seed 1, after fix):
  rod-center mean step:  CPU 5.46 nm   GPU 5.51 nm   -> now MATCH (was 17.42 vs 5.51)
